# Beacon Motive delivery roadmap

Reviewed November 2, 2026 against source, development records and GitHub. Nothing is production ready. **Implemented** means code exists; evidence in each row states whether it was exercised in a deterministic fixture, a real app, an emulator or a physical device. A fixture/build pass does not establish general app/device support.

## Where development stopped

The current branch is `codex/portable-workspace` at `ba8a8fb`, four pushed maintenance commits ahead of `main` (`717af66`) before this documentation review. The last feature commit on main, October 15, added optional local-model repair and its UI/API. Prior work includes browser/Windows teaching, Android, scheduling, the desktop shell, MCP and Windows OCR; this is well beyond an empty foundation.

November 1 maintenance moved private local state into the organized external root, verified the Windows helper and desktop builds, and recorded focused deterministic validation. The local API token was rotated and tested with the scheduler/workflows inactive; no workflow was run as a credential check. November 2 cleanup and independent encrypted recovery are complete. Motive remains local-only, with no Oracle deployment and no functional Beacon Remote connector.

The most useful next milestone is **human-operated Teach and Replay acceptance**, first on a supported browser task and then on a Windows app. The recorder code exists, but the full person-driven record/review/save/replay lifecycle still lacks the evidence described below. Choose a non-sensitive task, record it visibly, change its inputs, replay it and inspect the actual result. Fix the smallest demonstrated failure before adding another platform or model.

## Next work, in order

1. **Complete a real browser teaching session.** Have the owner choose a non-sensitive website/task and explicitly start recording. Use the CLI or desktop Teach screen; demonstrate finish/cancel, inspect the proposed steps/variables/scopes, save explicitly, replay with changed input and verify the page result. Use ordinary supported page controls first; then document iframe, new-tab and shadow-DOM failures instead of claiming those are supported. Secret-like fields must remain excluded and real credentials must not enter recordings/history.
2. **Complete the Windows teaching session.** Run the same visible record/review/save/replay loop on a chosen non-elevated app, including real mouse/keyboard actions and Ctrl-C/cancel. Existing Calculator/WinForms examples establish a narrow baseline. Investigate missed control events only after reproducing them; retain shell-launch refusal, password-read refusal, app scopes and emergency Stop. DPI/multi-monitor and WPF/Qt/Electron/Java coverage are separate acceptance work.
3. **Make the demonstrated Windows path distributable.** Scope packaging around the existing Tauri shell and native helper. The current Tauri config has bundling disabled and the app still needs the checkout/Node runtime; a successful release executable is not an installer. Define bundled runtime/helper discovery, private data location, signing, install/upgrade/uninstall and clean-machine acceptance before changing packaging. Deterministic CI is implemented in the November 2 follow-up below; keep desktop-interacting fixtures out of routine hosted checks.
4. **Validate the existing integrations with real clients/devices.** Try Motive's allowlisted stdio MCP server with a real MCP client; no secret inputs through MCP and no implicit workflow authority. Revisit physical Android helper/permission/recovery behavior when an authorized phone is available. Keep audio tests excluded. A running local API may use old source: identify its owner/version and stop it through its own workflow before retesting.
5. **Expand only after the current path works.** Resolve cross-platform dependency gates before Linux desktop packaging. Treat OpenAdapt import, additional browser targets, advanced selectors, events/triggers, new platforms and model/vision providers as separately scoped work. Remote integration depends on Remote's consented session/automation milestone; sharing a suite name grants no authority.

### November 2 development follow-up: deterministic CI

The new GitHub Actions workflow checks locked dependency installation, TypeScript, deterministic boundary regressions and root/desktop JavaScript audits on Windows and Ubuntu. Third-party actions are pinned to verified commit SHAs, repository permission is read-only and checkout credentials are not persisted. No production credentials or signing secrets are provided.

The existing local-API authentication/Host/Origin regression was moved out of the application-driving integration file into a core-only test. Its workflow polling now fails if the run never reaches a terminal state. Existing Android package-filter/selector tests were also separated from device opt-ins into a parser-only file so CI checks notification/package isolation without adb. Other device/browser/manual tests remain available through the original full suite and are excluded from `test:ci`; they were not replaced by mocks. Local typechecking, deterministic regressions and both JavaScript audits passed. Hosted checks also passed on Windows 2025 and Ubuntu 24.04 at `61f5f18`; see development-status.md for the exact run and remaining acceptance gates.

## Working boundaries

The engine must remain useful with no AI provider installed. Model suggestions are optional, loopback-only, validated proposals requiring human application; false-positive behavior prevents any claim of autonomous repair. Keep scopes narrow, the API authenticated on loopback, secret redaction, visible recording/review, cancellation and emergency Stop. No shell operation, inherited Remote permission, production workflow run, phone input or audio test is part of this documentation review. See [workspace.md](workspace.md), [development-status.md](development-status.md) and the security ADRs before acting.
